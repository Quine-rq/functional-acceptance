# 分页导出验收方案（仅方案）

用户需要把本地分页 JSON 的全部记录导出为一个新 CSV，供其他程序原样读回；任何失败都不能覆盖用户原有文件。本方案以 `requirements.md` 为验收合同，以预先冻结的 `fixtures/expected_records.json` 为独立真值。

本次仅阅读指定技能及项目的需求、README、入口 `export.py`、原生测试 `test_export.py` 和三个 fixture，未运行 Python、导出、测试、材料工具或环境探测，未修改项目。所有运行结果目前均为 **UNVERIFIED（未验证）**。使用 functional-acceptance 技能确定了独立读回、需求逐项覆盖、执行前提和缺口的交付方式；本方案不准备辅助工具材料，因此不需要读取其材料格式引用或运行辅助工具。

## 1. 固定验收口径

实际入口为 `export.py --source <输入> --output <新路径>`，正常路径应返回 0；正常可处理的参数、输入和文件错误按项目约定返回 2，并在 stderr 给出可理解的错误文字。

健康输入固定为 3 页、5 条记录，ID 顺序严格是 `r-001,r-002,r-003,r-004,r-005`，每条恰好一次。CSV 以 UTF-8 解码，表头严格为 `id,title,notes`，字段逐项与独立期望相等，保留中文、emoji、逗号、双引号、空字符串以及字段内 LF、CRLF。不以进程成功、文件存在或物理行数代替内容完整性检查。

空集合和合法空记录页都应成功生成只有表头的 CSV；缺少 CSV 是验收缺口，不能解释成空结果。输出必须是父目录已存在的新路径。已有文件、目录、正常或悬空符号链接、源文件本身一律不得被替换。

这是完整分页集合已给出的合成输入，验证边界为真实 Python CLI、分页遍历、CSV 编码和本机落盘。网络请求、远端 API、存储服务、账号权限、真实业务数据、下载和筛选不在该需求范围，不将它们计为通过。

## 2. 执行前提与复用方式

后续取得执行授权后，先确认实际 Python 路径和版本、操作系统、输入与独立期望的文件身份、运行目录和输出目录的绝对路径。项目说明要求 Python 3.8+、支持同目录硬链接的本地文件系统；同时检查目录可写、可用空间及符号链接、FIFO 能力。不能依据当前会话能读文件，就推断目标机器满足这些条件。

技能的实验辅助工具另外要求 Python 3.10+ 和 POSIX 文件系统，不能把它的条件套到原生 CLI，也不能假定当前机器兼容。优先复用项目原生检查，本轮方案无需辅助工具、安装依赖、账号或联网。若未来决定使用辅助工具，届时先读其材料格式并确认运行支持，不能把任意日志直接包装成受支持的断言。

原生检查入口如下，仅供未来执行，本次未运行：

```sh
cd examples/paginated_export
python3 -B -m unittest discover -s . -p 'test_export.py' -v
```

执行时将 `python3` 对应到已经确认的解释器。现有测试用 `sys.executable` 启动实际 CLI 子进程，不导入导出器内部函数；每次使用独立临时目录，子进程超时为 10 秒。直接复用这些机制，不改 fixture、期望或项目测试去迎合输出。

原生测试退出时会清理其临时产物。因此测试日志可证明它执行了哪些断言，但不等于交付了可再次打开的 CSV。后续验收应另在本次运行专属的新目录保留健康、缺陷、空结果三份导出及读回证据。对应原生命令形式为：

```text
<已确认的Python> -B export.py --source fixtures/pages.json --output <运行目录>/healthy.csv
<已确认的Python> -B export.py --source fixtures/pages.json --output <运行目录>/defective.csv --fault omit-final-page
<已确认的Python> -B export.py --source fixtures/empty_pages.json --output <运行目录>/empty.csv
```

这些是命令模板，需从上述项目目录执行，替换成真实解释器及新路径；记录模板不构成执行授权。额外异常输入、故障驱动和哨兵文件也只放入独立运行目录，不能拿用户真实文件做破坏性试验。

## 3. 检查矩阵与观察位置

| 要求与场景 | 独立预期和观察 | 已有检查复用及需要补齐的部分 |
| --- | --- | --- |
| 健康分页与字段完整性 | CLI 返回 0；进程结束后重新打开实际 `healthy.csv`，核对表头、5 条完整记录及 ID 顺序，特别是末页 `r-005`；源文件前后字节相同 | 复用 `test_healthy_export_preserves_all_pages_and_exact_csv_fields`、`read_records`、`assert_complete_export` 的做法。用 UTF-8、`newline=""` 和 `csv.DictReader` 读回，与独立 JSON 列表作完整相等比较，既核数量、顺序，也核每个字段 |
| 缺页反证 | 显式缺陷开关仍返回 0，但文件只有前两页的 4 条，缺 `r-005`；同一完整性检查必须失败 | 复用 `test_fault_returns_zero_but_fails_the_same_completeness_check`。测试套件成功检出缺陷可以通过，但这次缺陷导出的业务结果必须标 **FAIL**，不能被套件总结果掩盖 |
| 空结果与缺失文件 | `pages: []`、一页空 records 均返回 0，文件存在、表头正确、数据记录为 0；不存在的产物不能通过 | 复用两项 empty 测试与 `test_missing_artifact_cannot_satisfy_the_completeness_check`。空集合已有原始字节断言 `id,title,notes\r\n`，空记录页也补查无多余数据 |
| 输入大小与解析 | 2,097,152 字节合法 UTF-8 普通文件可成功；2,097,153 字节拒绝。非法或过深 JSON、重复键、非法 UTF-8 均友好非零，无最终 CSV | 复用 at-limit、too-large、deeply-nested、invalid-json、duplicate-keys、invalid-unicode 测试。已有 invalid-unicode 检查的是 JSON 中无法编码的代理字符，需另补真实非法 UTF-8 字节；补页对象和记录对象内部重复键。所有错误分支统一核 stderr、无 traceback 和无最终路径 |
| 结构、页序和 ID | 根对象只有 pages 数组；每页恰含 page、records，页号从 1 连续递增且不是布尔值；每条恰含三个字符串字段，ID 非空、跨页唯一 | 复用 invalid-schema 测试及 `test_fault_does_not_hide_invalid_final_page`。补根/页多余字段、页非对象、记录非对象、同页重复 ID，以及多页中间跳号、重复或倒序，防止仅第一页校验通过 |
| 源对象与参数错误 | 缺失源、目录、源符号链接和悬空链接、FIFO 等非普通文件被拒绝，无等待管道写者；参数错误有友好错误且无输出 | 复用 missing-source、source-symlink、source-named-pipe、unknown-fault 测试。若符号链接或 FIFO 检查被跳过，对应覆盖记 UNVERIFIED；必要时补缺失必填参数。其他可构造的特殊文件拒绝仍需单列观察，不能把 FIFO 等同于全部特殊类型 |
| 原文件和路径保护 | 已有普通文件字节不变；目录及其中的哨兵内容不变；链接对象和目标内容不变，悬空链接仍悬空；source=output 拒绝且源字节不变；缺失父目录不自动创建 | 复用 existing-file、source-as-output、existing-directory、output-symlink、missing-output-parent 测试。目录现有测试只检查空目录，补非空目录哨兵。用不跟随链接的路径检查识别悬空链接，不能仅凭 `exists()` 判断无最终路径 |
| 排他发布与并发 | 两个进程争用同一个新输出，返回码应为一成一败，即 `[0,2]`；最终文件仍与 5 条完整期望相等，没有拼接或部分文件 | 复用 `test_concurrent_same_output_has_one_winner_and_a_complete_file`，记录两个 PID、退出码、stderr、最终文件及临时文件清单。进程均终止后才判断结果或清理 |
| 文件错误、发布失败与恢复 | 同目录临时写入完成后才能排他发布；写入/同步/发布失败应明确非零，发布前失败不得生成最终 CSV，原文件仍受保护；硬链接不支持时不得降级覆盖 | 当前套件未直接验证硬链接不支持、写入中断、磁盘空间不足、fsync 错误或发布后临时文件清理失败。后续在隔离目录用经检查的故障驱动或合适测试文件系统验证，记录所替代的边界；模拟错误不能算真实磁盘故障通过。无法构造的分支保留 UNVERIFIED |

完整性检查的预期只能来自需求和预先冻结的 `expected_records.json`，不得由本次 CSV 的记录数、内容或导出器常量反推。逐字段比较时禁止去空白、转换换行、Unicode 归一化或“清洗”；这些操作会掩盖字段变化。额外列、少列、空字段变化和行序变化都应暴露。

## 4. 异常时保护原文件与处理残留

静态实现已呈现“完整输入校验 → 内存编码 → 输出父目录内创建 `.export-*.tmp` → 写入并 flush/fsync → `os.link` 排他发布 → 删除本次临时文件”的路径；这支持检查设计，但不构成该机器上的执行证明。

每个保护场景开始前，保存运行目录内哨兵文件的原始字节、路径类型、链接目标和目录内容清单；场景结束后分别核对。已有文件校验必须同时覆盖正常和缺陷导出模式。只要有既存目标被替换，就是 FAIL，即使新 CSV 内容正确也不能通过。

输入校验失败应没有最终路径，也没有本次临时文件。正常可处理的写入或发布错误应核实临时文件清理。发生超时、强制终止或中断时，先确认所有本次写进程的终止状态，再检查已知最终路径和临时路径；不能先删除、重试或把残留临时文件当成完整结果。

发布可能先成功，而后续临时文件删除失败，此时可能出现“非零退出，但完整最终文件已存在”。必须读回已知最终文件并记录其内容及残留，不能据非零退出码声称未产生副作用。恢复仍遵循新路径原则，绝不能覆盖这个已存在路径；状态不明时交接 PID、路径和下一步只读观察，不自动重跑整个场景。

强制终止、掉电和真实磁盘故障的清理与持久性不在现有测试证明内。若后续执行这些故障检查，限本次目录，不要求自动清理守护进程，也不把文件 fsync 直接解释为断电后目录项持久性的证明。清理前确认写进程全部结束，仅按明确完整文件名删除本次产物；保留证据的文件在约定保留期后再处理，不递归清空其他目录。

## 5. 证据、判定与当前缺口

后续每项检查记录：需求编号、场景和尝试编号、真实解释器及平台、输入/期望身份、命令和工作目录、输出绝对路径、起止时间、PID 和最终退出状态、stdout/stderr、独立读回结果、原文件保护对比及残留清单。日志和保留文件置于同一个新运行目录，失败后再成功也保留两次记录；哈希只辅助确认文件变化，不能代替内容比对或证明采集真实性。

逐项结论使用 PASS、FAIL、UNVERIFIED；只有需求明确排除的能力才可注明来源后标 NOT_APPLICABLE。任何测试 skip、文件缺失、环境不符或故障分支未执行都保留未验证状态。真实反例不被后一次成功抵消。原生测试总通过不能自动等于所有需求通过。

当前只能确认需求、入口和现有测试的静态对应关系。以下事项尚不能确认：目标机器 Python 和文件系统是否满足条件；原生测试是否通过或跳过；实际 CSV 是否完整且字段无变化；原文件在错误和并发时是否保全；缺少的故障检查结果及异常清理状态。尚无运行证据、真实 CSV 产物或另一位执行者的复现，因此不声称验收通过、可上线或独立交接已验证。
