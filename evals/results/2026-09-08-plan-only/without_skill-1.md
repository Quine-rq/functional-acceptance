# 分页导出验收方案（仅方案，待执行）

用户要把已提供的本地分页 JSON 全部导出到一个新 CSV，其他程序读回时记录和字段完全一致；任何失败都不能覆盖已有文件。本次只根据输入目录的 `requirements.md`、`README.md`、`export.py`、`test_export.py` 和三个 fixture 制定方案，没有运行 Python、导出、测试或材料工具，没有修改项目文件。

## 1. 验收依据与范围

以 `requirements.md` 为验收标准。已静态确认健康输入有 3 页、5 条记录，ID 顺序为 `r-001,r-002,r-003,r-004,r-005`。独立期望为预先冻结的 `fixtures/expected_records.json`，不得通过导出结果、导出器内部函数或本次动态拼接源分页来重新生成期望，也不得为使测试通过而改动 fixture。

本样本覆盖本地合成分页集合、真实 Python CLI、CSV 编码和实际文件落盘。没有下载、筛选、网络分页、远端 API、账号或真实业务数据，不将这些能力计入验收结论。实际运行环境尚未确认，当前所有执行结果均为“待验证”。

## 2. 执行前置条件与顺序

后续获得执行授权后，先确认 Python 3.8+ 可用，标准库可正常加载；确认可创建专用临时目录，目标父目录已存在且可写，目标所在文件系统支持同目录硬链接。符号链接、命名管道及并发进程能力需记录；不具备能力时标为未验证，不把跳过当作通过。另行确认源文件为 UTF-8 普通文件、不是符号链接，大小不超过 2,097,152 字节，包含等于上限的情况。

顺序为：确认环境 → 运行已有原生检查 → 核对失败、跳过及覆盖缺口 → 按缺口安排受控补验 → 汇总用户结果与证据。所有运行输入副本和输出使用专用临时目录，正常输出选择尚不存在的新路径；覆盖拒绝测试只使用该目录中专门创建的哨兵文件或链接。

优先复用现有命令，从输入项目目录执行，以下仅为将来执行说明，本次未运行：

```sh
python3 -B -m unittest discover -s . -p 'test_export.py' -v
```

现有测试使用 `unittest`、真实 CLI 子进程和标准 CSV 读取器，不导入 exporter 实现，也不需要安装依赖或联网。无需重写一套相同的验收工具。测试失败先检查具体断言、stderr 和运行条件，不调整固定期望迁就输出。

## 3. 怎样确认 CSV 完整且字段没有变化

复用 `read_records()` 与 `assert_complete_export()`：以 `encoding="utf-8"`、`newline=""` 打开实际生成文件，通过 `csv.DictReader` 读回；先断言表头按顺序恰为 `id,title,notes`，再将完整记录列表与独立期望逐项比较。

通过标准必须同时满足：CLI 返回 0，最终文件确实存在且可读，恰有 5 条记录，ID 顺序完全一致且每条只出现一次，最后一页的 `r-005` 存在，所有字段逐字符相等。中文、emoji、逗号、双引号、空字符串、LF 和 CRLF 都必须保留。记录比较不得排序、去重、裁剪空白或统一换行；不能用文件行数统计记录，因为字段自身包含换行。

复用同一完整性断言验收显式缺陷 `--fault omit-final-page`：它预期返回 0，但只有前两页的 4 条记录、缺少 `r-005`，因此内容验收必须失败。对应 unittest 通过表示检查正确检出了缺陷，不表示缺陷导出业务通过。

空结果分别验证 `pages: []` 和合法的空记录页：返回 0，文件存在且只有表头，读回记录为零。现有空集合测试还核对精确字节 `id,title,notes\r\n`。缺少产物不能解释为空结果；复用现有缺失产物测试，必须判为无法通过完整性检查。

## 4. 复用现有检查及需要补齐的证据

| 要求 | 现有原生检查 | 验收判定与补验重点 |
| --- | --- | --- |
| 全页与字段一致 | 健康导出、缺页反证、精确表头和完整记录列表比较 | 健康必须通过同一内容检查；缺页必须被拒绝 |
| 空结果与产物存在 | 空分页集合、空记录页、缺失产物 | 空结果有表头；无文件不能通过 |
| JSON 和结构校验 | 破损 JSON、重复根键、非法根结构、页号从 2 开始或为布尔值、records 非数组、缺字段/额外字段/非字符串、空或跨页重复 ID | 非零且有友好错误，无最终 CSV；后续补核非法 UTF-8 字节、页中/记录中重复键、根/页多余字段、页序跳号或重复等未直接覆盖变体 |
| 大小和深度边界 | 恰好 2 MiB 成功、超 1 字节拒绝、深嵌套拒绝 | 深度阈值可能随 Python 版本变化；要求友好非零错误，不泄露 traceback，不留下最终 CSV |
| 源文件安全 | 健康导出前后字节相等、缺失源、目录、源符号链接/悬空链接、命名管道、源输出同路径 | 不阻塞读取特殊文件；源及链接保持原样；报告能力跳过 |
| 既存目标保护 | 文件、目录、普通链接、悬空链接；文件覆盖拒绝含健康与缺陷模式 | 非零；原文件字节、目录及链接目标保持不变，悬空链接不能被创建目标或替换 |
| 新路径和并发发布 | 缺少父目录、两个进程同名输出 | 不自动建父目录；同名两个进程恰为一个成功、一个失败；最终文件通过完整内容检查，无自身临时文件残留 |
| 文件故障和发布失败 | 多项测试检查 `.export-*.tmp` 清理，但无专门磁盘写满、写入/fsync 失败、硬链接不支持或清理失败测试 | 后续在独立目录或受控故障环境补验；当前不能据静态代码声称这些路径实测通过 |

对所有正常可处理的输入/文件错误，统一检查非零退出码与可理解的错误文字；项目约定返回 2，已有部分用例只检查了退出码，后续应补核 stderr。校验失败必须不创建最终 CSV。参数缺失、未知故障参数等也应有明确错误；已有未知故障参数用例可直接复用。

补验仅是计划，不在本次增加测试或创建故障材料。运行规模限于此合成样本，不能从一次并发测试推断任意并发规模或所有文件系统都已可靠。

## 5. 异常时怎样保护原文件

从当前实现静态可见，输入全部校验并完成 CSV 编码后，程序才在目标同目录创建 `.export-*.tmp`，写完、flush、fsync 后以 `os.link` 排他发布，再清理自身临时文件。目标存在性预检查包含悬空链接；真正的竞争保护来自排他发布，不能只验收“先检查不存在”。这些是待实测的实现机制，不是运行成功证据。

后续验收应覆盖以下保护和恢复结果：

1. 在沙盒中预先保存源文件和目标哨兵文件的原始字节；执行前后比较。链接同时核对类型与链接指向，目录放置哨兵子项并核对保留情况。拒绝覆盖后不自动改名、删除原目标或重试覆盖。
2. 输入校验、编码、临时写入或发布前失败时，要求无本次最终 CSV、原文件不变，正常可处理错误清理本次临时文件。硬链接不可用或发布时目标被别人抢先创建，必须报错且保留现有目标，不能退回覆盖写入。
3. 发布成功后若临时文件清理失败，需要单独核查：当前执行顺序可能出现“最终文件已发布，但退出非零”。此时先读回最终文件核实完整性并报告实际状态，不能把非零自动解释成无产物，也不能删除该目标后覆盖重跑。必要的重试使用另一个明确的新路径。
4. 强杀进程、掉电或磁盘故障可能留下临时文件；临时文件不算已完成产物。恢复时先检查最终路径是否存在及内容是否完整，再决定是否使用新路径重试。当前方案不承诺断电后的持久性，也不安排在真实用户目录中制造破坏性故障。
5. 清理只处理本次专用目录中逐个确认属于本次运行的明确文件路径；不用递归清空或通配符删除。先保留需要的证据，再删除已确认的运行产物和空目录；不删除源 fixture、既存文件或未知残留。
